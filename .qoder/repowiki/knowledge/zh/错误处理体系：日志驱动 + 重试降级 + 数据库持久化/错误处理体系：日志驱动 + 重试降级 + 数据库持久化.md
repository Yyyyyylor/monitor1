该仓库未定义统一的自定义异常类型或错误码枚举，而是采用「日志记录 + 返回值 None/布尔 + 数据库失败计数」的组合策略来处理各类错误。具体模式如下：

1. **网络层错误（crawler/fetcher.py）**
   - HTTP 请求使用 httpx，对 429/403/非 JSON 响应等可预期状态通过 `logger.warning` 记录并返回 `None`，由调用方判断；对超时、连接错误、协议错误等异常在达到 `max_retries` 后重新抛出（`raise`），不吞掉底层异常。
   - 指数退避重试：`await asyncio.sleep(2 ** attempt)`，配合 `settings.max_retries` 控制最大尝试次数。
   - 成功路径返回结构化字典，失败路径统一返回 `None`，调用方通过 `if data is None` 分支处理。

2. **代理检测错误（crawler/proxy.py）**
   - 端口探测、注册表读取、DNS 解析等可能失败的步骤均用 `try/except` 包裹，捕获 `OSError`、`TimeoutError`、`socket.gaierror` 等具体异常后静默降级，最终回退到直连模式。

3. **数据库层错误（db/database.py, db/repository.py）**
   - Schema 迁移 SQL 执行时捕获 `Exception` 并忽略（列已存在则跳过），保证启动鲁棒性。
   - 会话操作通过 `async with async_session_factory()` 上下文管理器自动管理事务，异常会触发回滚。
   - 失败计数与最近错误消息持久化到 `MonitoredUser.last_error_msg` 和 `consecutive_fails` 字段，提供 `record_failure` / `reset_failure_count` 接口。

4. **应用级错误传播**
   - CLI/Web 入口（`main.py`、`run_web.py`）仅捕获 `KeyboardInterrupt` 用于优雅退出，其他异常直接向上冒泡，由进程外监控（systemd/Docker）感知。
   - 健康检查服务（`health/server.py`）暴露 `/health` 和 `/ping` 端点，返回运行状态而非抛异常。

5. **日志系统（utils.py）**
   - 统一通过 loguru 初始化，同时桥接标准 `logging` 模块，所有模块使用 `logging.getLogger(__name__)` 输出结构化日志。
   - 日志按日轮转、保留 30 天、gzip 压缩，便于问题回溯。

6. **配置校验错误**
   - 使用 pydantic-settings 的 `BaseSettings`，非法配置会在导入时抛出 `pydantic.ValidationError`，无自定义包装。

**约定与约束**
- 外部 API 调用失败优先返回 `None` 而非抛异常，由上层决定是否重试或告警。
- 不可恢复的网络异常（httpx.TimeoutException/ConnectError/RemoteProtocolError）在重试耗尽后必须 `raise`，不得吞掉。
- 数据库操作必须通过 `async_session_factory()` 上下文管理器，禁止手动管理 session 生命周期。
- 所有用户可见的错误信息需先经 `record_failure` 持久化，再决定是否触发管理员通知（阈值由 `consecutive_fail_threshold` 控制）。
